2. Distinct client requests, and how retries avoid being double counted
   unique valid access lines ......... 720
   distinct request_id values ........ 720
   upstream attempts recorded ........ 739   <- NOT the request count
   error.log lines carrying a request_id 67   <- NOT the request count

   One access line == one client request, written once when the client
   response completes. A retry adds a value to `upstream`, not a line:
   19 requests carry 2 upstream attempts. Counting attempts would report
   739 requests instead of 720.

   Independent cross-check from the other side of the proxy:
     unique application http_request records .......... 680
     requests with no application record at all ....... 40
     sum ............................................. 720
   which equals the 720 distinct client requests. The 40 with no application
   record are exactly the requests the backend never received.

5. Median and p95 client latency
   Units: access.log `request_time` is SECONDS; application.log
   `duration_ms` is MILLISECONDS. They agree - e.g. lab-000292 is
   request_time 2.025 and duration_ms 2025.0 - so they must never be
   pooled into one sample.
   Method: nearest-rank percentile on the sorted sample, which always
   returns a measurement that actually happened. No interpolation.
   all requests       n=720  median 0.054s   p95 2.001s   p99 2.025s   max 2.025s
   2xx/3xx/4xx only   n=625  median 0.055s   p95 0.093s   p99 0.120s   max 0.120s
   5xx only           n=95   median 0.041s   p95 2.025s   p99 2.025s   max 2.025s
   The headline p95 is set entirely by the failing minority: successful
   requests sit at 0.093s p95 while the 5xx tail sits at 2.025s, the
   ~2s dependency timeout inside the application.

9. Proxy/connectivity failures versus dependency/application failures
   The three signatures are separable, and each is proved by a different
   file agreeing or staying silent:

   502 - PROXY/CONNECTIVITY. error.log has a connect() failed (111) line
         for the request; application.log has no record of it at all.
         Proof: 40 of the 40 requests that ended 502 have zero
         application-log rows. The backend process was not listening, so
         it could not have logged anything.

   503 - DEPENDENCY/APPLICATION. error.log is silent; application.log
         carries an explicit dependency_error with the dependency name
         and exception type, immediately followed by the 503 http_request
         row for the same request_id. The app was healthy enough to
         diagnose its own failure and answer. Both instances were hit,
         which points at the shared dependency rather than one backend.

   504 - PROXY GAVE UP ON A SLOW BACKEND. error.log has 'upstream timed
         out (110) while reading response header'; application.log has no
         completion row for those requests, because the app had accepted
         the connection and had not finished. This is the ambiguous case:
         the work may well have been done and only the answer was lost.
         For /records, a write, that ambiguity is the reason a proxy
         should not blindly retry POSTs.

   Latency separates them again: 502s are fast (a refused connect is
   immediate), 503s cluster at ~2.02s (the app's own dependency timeout),
   504s at the proxy's read timeout.

10. What the logs do not prove, and what to check next
   Not proved by these files:
   - WHY app-02 stopped accepting connections. A refused connect proves
     nothing was listening; it does not distinguish a crash, an OOM kill,
     a deploy, or a container that was simply stopped. No exit code, no
     restart count and no kernel log is present here.
   - WHY Redis timed out. TimeoutError is the client's view. Server-side
     saturation, a blocking command, an AOF rewrite stall and a network
     drop all look identical from this side.
   - Whether the PostgreSQL InvalidPassword burst was a rotated secret, a
     partially rolled-out config, or a wrong value in one environment.
     16 failures on both instances inside 98 seconds fits a credential
     change far better than it fits a network fault - but that is an
     inference, not evidence.
   - Whether the 8 timed-out /records writes were committed. The proxy
     gave up before the answer arrived; the logs cannot say what the
     database did.
   - Anything about a second client. Every line has client 192.0.2.24, so
     these numbers describe one synthetic generator, not real user traffic.

   What I would check next in a running environment:
   - docker inspect app-02 for State.ExitCode, OOMKilled and RestartCount,
     and `docker events` around 11:05:02.
   - Redis INFO commandstats / latency history / slowlog, and whether an
     AOF rewrite or a maxmemory eviction coincided with 11:12.
   - The PostgreSQL server log for FATAL password authentication failed,
     which names the role and the client address the app log cannot.
   - Whether rows exist for the 8 timed-out /records requests, which
     settles the duplicate-write question the 504s leave open.
   - Resource limits and host pressure for the whole window: none of these
     logs carries CPU, memory or connection-pool data.
